`nest-graph-inspector export` writes your application's dependency graph to a
file without starting the application. Use it wherever running it is
impractical: in CI, in a code review, or on a machine without the database,
queue, or secrets it needs to start.

## Export the graph

Build your project, then run the export from the project's root:

::code-group
```bash [npm]
npx nest-graph-inspector export
```

```bash [yarn]
yarn nest-graph-inspector export
```

```bash [pnpm]
pnpm exec nest-graph-inspector export
```

```bash [bun]
bunx nest-graph-inspector export
```
::

```txt [Output]
nest-graph-inspector: exported AppModule (8 modules, 13 providers, 3 controllers, 4 cycles) to nest-graph.json (booted in Nest preview mode: nothing was instantiated)
```

`nest-graph.json` holds the same `GraphOutput` document a running inspector
serves at `/output.json` — same shape, same schema version — so anything that
reads one reads the other.

Your application does not need to import `NestGraphInspectorModule` for this:
`npx nest-graph-inspector export` works in any NestJS project. When it does
import it, keep the package installed in the project; the export then runs
with the copy your application uses (see
[Options from your application](#options-from-your-application)).

## If `main.ts` loads your environment

The export loads your root module, never `main.ts`. If `main.ts` loads
environment variables before it imports `AppModule` — `import 'dotenv/config'`
on its first line, say — and a module file reads them as it loads, hand the
export the same environment:

```bash [Terminal]
npx nest-graph-inspector export --env-file .env
```

`--env-file` needs Node.js 20.12 or later and can be repeated. As with
`node --env-file`, a variable already set in your environment keeps its value,
and of two files the later one wins. On an older Node.js, or to load the
environment exactly as your `main.ts` does, require dotenv instead:

```bash [Terminal]
npx nest-graph-inspector export --require dotenv/config
```

Without either, the export stops where your application would: with the error
your configuration throws for the missing variable.

## How it works

The export boots your application in NestJS's **preview mode**, the mode Nest
itself provides for
[drawing an application's graph in CI](https://docs.nestjs.com/devtools/ci-cd-integration).

::steps
### Load your module files
The compiled file that exports your root module — `dist/app.module.js` — is
loaded with `require()`, and with it every module file it imports. `main.ts`
is never loaded, so `bootstrap()` never runs.

### Boot in preview mode
`NestFactory.create(AppModule, { preview: true, snapshot: true })`. Nest scans
every module and resolves every dependency — a provider it cannot resolve fails
the export, as it would fail your application — but calls no constructor, no
`useFactory`, no lifecycle hook (`onModuleInit`, `onApplicationBootstrap`,
`onModuleDestroy`, …), and no `configure()`. The application is never
initialized, and never listens on a port.

### Build the graph
The graph is built by the same code that serves `/output.json` in a running
application, with the options your application passes to
`NestGraphInspectorModule.forRoot()`. JSDoc and Direct Run parameter types are
read from your TypeScript sources, as they are at runtime.
::

## Options

| Option | Default | What it does |
|---|---|---|
| `--entry <file>` | Detected | The file that exports your root module: compiled JavaScript, or TypeScript with a `--require` loader. Detected from `nest-cli.json` (`sourceRoot`) and the `outDir` of the tsconfig `nest build` uses: `dist/app.module.js`, `dist/src/app.module.js`, or the only `app.module.js` under the output directory |
| `--module <name>` | `AppModule` | The export name of the root module class. Without it, a file that exports no `AppModule` but exactly one Nest module uses that one |
| `-o, --out <file>` | `nest-graph.json` | Where to write the graph; `-` writes it to stdout |
| `-p, --project <dir>` | The current directory | The project root. The export runs from there, so `.env` files and `tsconfig.json` are found as when the application starts |
| `--env-file <file>` | — | Environment variables to load before anything else, for an application whose `main.ts` loads them; see [above](#if-maints-loads-your-environment). Repeatable; Node.js 20.12 or later |
| `-r, --require <module>` | — | A module to load first, resolved from the project, such as `ts-node/register` or `dotenv/config`. Repeatable |
| `--compact` | Off | Write the JSON on one line, byte for byte as `/output.json` serves it, instead of indented |
| `-h, --help` | | Show the help |
| `-v, --version` | | Show the version |

`--entry`, `--out`, `--project`, and `--env-file` are relative to the directory
you run the command from.

::callout{icon="i-lucide-triangle-alert" color="warning" title="Never point --entry at main.js"}
The export loads whatever file `--entry` names. `main.js` calls `bootstrap()`,
so loading it starts your application. Point it at the file that exports your
root module.
::

### TypeScript, without building

```bash [Terminal]
npx nest-graph-inspector export --entry src/app.module.ts \
  --require ts-node/register --require tsconfig-paths/register
```

The loader has to emit decorator metadata, which is what Nest reads
constructor dependencies from. `ts-node` does. esbuild-based loaders such as
`tsx` do not, and SWC does only with `decoratorMetadata` enabled; without it,
Nest sees only the dependencies injected with an explicit `@Inject()` token,
and the graph silently lacks the rest.

### On standard output

```bash [Terminal]
npx nest-graph-inspector export --out - --compact > graph.json
```

Only the graph goes to standard output. The summary, warnings, Nest's own
errors, and anything your application writes through `process.stdout` —
`console.log` in a module file, Nest's logger, even a timer that fires after
the export — go to standard error. A logger that writes straight to file
descriptor 1, such as pino with `pino.destination(1)`, is beyond the
export's reach: write the graph to a file instead.

### Exit codes

| Code | Meaning |
|---|---|
| `0` | The graph was written |
| `1` | The export failed: no entry file, no root module export, or Nest could not bootstrap the application |
| `2` | The command line was invalid |

## Options from your application

The export builds the graph a running inspector would serve, so it uses the
options your application gives `NestGraphInspectorModule`:

- **`forRoot({ … })`, or a plain `NestGraphInspectorModule` import**: its
  `rootModule`, `ignore`, `nestCoreModuleName`, and `nestCoreProviders` are
  applied, and the root module is chosen the same way — `rootModule`, or else
  the module that imports the inspector.
- **No `NestGraphInspectorModule` at all**: the defaults, with your entry
  module as the root.
- **`forRootAsync()`**: its options come from a factory, and preview mode runs
  no factory, so they cannot be read. The export uses the defaults with your
  entry module as the root, and says so in a warning.

`outputs` play no part in an export; nothing is served and no file other than
the graph is written.

When the copy of `nest-graph-inspector` your project installed is not the one
you ran — a global install, or `npx nest-graph-inspector@latest` — the export
hands over to the project's copy, because only that copy recognizes the
`NestGraphInspectorModule` your application imports. A project copy too old to
include the CLI cannot take over: the export then runs with the defaults, with
your entry module as the root, and warns you to upgrade.

## Viewing the file

Open the [Graph Viewer](/view) and drop `nest-graph.json` anywhere on the page,
or press **Open Graph File** and choose it. The viewer opens the navigator on
it, and every module's deep dive and the Issues page work as they do for a
running application.

The file stays in your browser. The viewer reads it with the browser's own
file API: it is never uploaded, nothing is fetched on its behalf, and nothing
starts to serve it. Neither its name nor its contents are sent to the site's
analytics. The tab keeps the graph for a reload when it fits in the tab's
storage — about 1.5 MB of JSON; a larger graph asks to be opened again after a
reload. Files up to 20 MB open.

Any `GraphOutput` document opens, wherever it came from: an export, the `json`
output, or a running inspector's `/output.json` saved to disk. A graph in
format 2 or earlier asks for a newer export, and one in a format newer than the
viewer opens with a notice that something may be missing.

The file is also plain JSON for everything else: commit it and review its diff
when a change rewires modules, keep it as a CI artifact, or validate it against
the `GRAPH_OUTPUT_JSON_SCHEMA` the package exports.

### What a graph file cannot do

A graph file has no application behind it, so the viewer turns off what needs
one and says why where you would look for it:

- **Direct Run.** There is no instance to call. The drawer still lists each
  provider's methods.
- **Trace.** A trace records Direct Run calls against a running application.
- **Saving a layout to your project.** Arrange the graph as you like: the tab
  keeps the arrangement, and **Download layout** saves the
  `nest-graph-layout.json` a running inspector reads from beside your
  application.
- **AI Chat.** The chat reads the Markdown summary a running inspector serves
  at `/output.md` beside its graph, and a graph file does not include it.

## Limitations

### Your module files still run

Preview mode stops Nest from instantiating anything, but your module files are
still loaded, and loading a file runs its top-level code:

- Statements at the top level of any imported file run.
- Decorators are evaluated, and with them every dynamic module call in an
  `imports` array: `ConfigModule.forRoot()` reads your `.env` file,
  `TypeOrmModule.forRoot({ … })` builds its options, and a `forRoot()` that
  throws fails the export.
- `forwardRef()` callbacks run, and promises in an `imports` array are awaited.
- An environment variable read at import time must be set, as it must be for
  `nest start`: in your environment, or with `--env-file` or
  `--require dotenv/config`.
- Nest initializes the modules on its preview allowlist. In NestJS itself that
  is only its own `InternalCoreModule`, but a library can add its own module,
  whose providers are then constructed and whose hooks run.

### What a running application would add

- **Direct Run methods of `useFactory` and `useExisting` providers.** A
  running inspector reads a provider's methods off its instance: the value a
  factory returned, or the provider an alias points at. Preview mode calls no
  factory and resolves no alias, so these providers carry no `directRun` in an
  export.
- **Anything added at runtime.** Modules loaded with `LazyModuleLoader`, or
  providers registered from a factory or a hook, exist only once the
  application runs.

Everything else — modules, imports, exports, providers, controllers, their
dependencies, JSDoc, routes, and cycles — is the graph a running inspector
serves.

### Requirements

- **NestJS 10 or 11**, the package's supported range. NestJS 12 is not
  supported yet.
- **Node.js 20 or later.**
- **A build the export can load.** A webpack build, the default for a Nest CLI
  monorepo, bundles everything into `main.js`, which starts the application
  when loaded. Point `--entry` at your TypeScript root module with
  `--require ts-node/register` instead, or build with `tsc`.
- **ES modules** — `.mjs` files, and `.js` files under a `"type": "module"`
  package.json — are loaded with `import()`, everything else with `require()`.
  An ESM project written in TypeScript is simplest to build first:
  `ts-node/register` only handles CommonJS.
