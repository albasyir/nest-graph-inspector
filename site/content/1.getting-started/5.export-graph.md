`nest-graph-inspector export` writes your application's dependency graph to a
file without starting it — for CI, a code review, or a machine without the
database, queue, or secrets the application needs.

## Export the graph

Webpack bundles and TypeScript ES-module projects need a different setup — see
[Graph export requirements](/getting-started/requirements#graph-export).

Build your project, then run the export from the project's root:

::package-manager-command{command="export"}
::

```txt [Output]
nest-graph-inspector: exported AppModule (8 modules, 13 providers, 3 controllers, 4 cycles) to nest-graph.json (booted in Nest preview mode: nothing was instantiated)
```

`nest-graph.json` is the same `GraphOutput` a running inspector serves at
`/output.json`: same shape, same schema version.

The export works in any NestJS project, with or without
`NestGraphInspectorModule`. If yours imports it, keep the package installed (see
[Options from your application](#options-from-your-application)).

## How the root module is found

Without `--entry`, the export finds your root module itself, in this order.
Nothing is run to find it.

::steps
### The compiled `app.module.js`
Where `nest build` writes it, from `nest-cli.json`'s `sourceRoot` and the
`outDir` of the tsconfig `nest build` uses: `dist/app.module.js`,
`dist/src/app.module.js`, or the only `app.module.js` under the output
directory. A project this finds exports exactly as it always has.

### The module `main.ts` boots
Failing that, the export reads `main.ts` — the `entryFile` in the `sourceRoot`
that `nest-cli.json` names, `src/main.ts` by default — as text, without
running it, and finds the module passed to `@nestjs/core`'s
`NestFactory.create()`, `createApplicationContext()` or `createMicroservice()`.
It follows that module's import, with your tsconfig's `paths`, and loads the
file `nest build` compiled it to: under the tsconfig's `outDir`, beside the
source when there is none, or — built with SWC — under the `outDir` its
builder's `options` name, with their `outFileExtension`. For `--app`, the
installed Nest CLI decides whose builder that is — the application's own from
12.0.14, the top level's before — and without one installed both are looked
at. Names are read in their own scope, as JavaScript reads them, and
`import x = require()` as CommonJS resolves it.
::

The export says what it found on standard error:

```txt [Output]
nest-graph-inspector: entry dist/root.module.js (RootModule, from src/main.ts)
nest-graph-inspector: exported RootModule (4 modules, 9 providers, 2 controllers, 0 cycles) to nest-graph.json (booted in Nest preview mode: nothing was instantiated)
```

- **One file, several modules.** The export takes the one `main.ts` boots, or
  the one `--module` names.
- **Several root modules.** When `main.ts` boots two — an API and a worker,
  say — pass `--module` with its export name, or with the name `main.ts`
  gives it: an import alias (`import { RootModule as Worker }`) or a `const`
  it boots it through. Two of one export name, from two files, need that
  name, or `--entry` with the compiled file and `--module`.
- **A build in more than one place.** With an `outDir` and no `rootDir`, `tsc`
  infers where to lay out its output — TypeScript 6 from the tsconfig's
  directory, TypeScript 5 from the sources' — so `src/root.module.ts` can be in
  `dist/` and in `dist/src/` at once, one of them stale. The export then loads
  neither: pass `--entry`, build again into an emptied `outDir`, or load the
  TypeScript source with `--require`. Setting `rootDir` avoids it.
- **A `NestFactory` of your own** — an object of yours, a parameter or local
  that shadows the import, a `let` alias later assigned something else, or a
  `require` of your own — boots nothing.
- **`RootModule.forRoot(…)`** is exported as `RootModule`, without its
  options, with a warning.
- **A root module declared in `main.ts` itself**, as `nest new --minimal`
  writes it, is refused: loading it would mean loading `main.ts`, which starts
  the application. Move it into a file of its own.
- **When the two disagree** — `dist/app.module.js` exists, but `main.ts` boots
  another module, directly or through re-exports — the export keeps to
  `dist/app.module.js` and warns, naming the `--entry` and `--module` that
  export the other — or, when the other is built to more than one file, or to
  one another application's build writes too, those files and its TypeScript
  source instead. Re-exports are read as JavaScript reads them, an explicit
  export of a name winning over an `export *`, three files deep at most; past
  that there is no warning, so pass `--entry` and `--module` when it matters.
- **When the export cannot tell** — no `main.ts`, no `NestFactory` call, or a
  root module known only at runtime — it asks for a build or `--entry`, as
  before. When `main.ts` also boots one it can follow, it exports that one and
  says which boot it passed over:

```txt [Output]
nest-graph-inspector: entry dist/root.module.js (RootModule, from src/main.ts)
nest-graph-inspector: skipped src/main.ts:8 NestFactory.createApplicationContext(rootFor(process.env.APP)): its root module is not an import the export can follow
```

### Not built, or bundled

When the root module has no compiled file to load — the project is not built
yet, or webpack or rspack bundled it into one `main.js` that starts the
application — any `--require` makes the export load its TypeScript source.
Without one, it stops and prints the command to run:

```txt [Output]
nest-graph-inspector: The project is built with webpack into one main.js, which starts the application when it is loaded. Its root module is AppModule in src/app.module.ts. Run: nest-graph-inspector export --require ts-node/register
```

The command adds `tsconfig-paths/register` when your tsconfig maps `paths`,
and starts with `TS_NODE_PROJECT=<tsconfig>`, POSIX shell style, when your
application builds with a tsconfig other than `tsconfig.json`, so both loaders
read the right one. The export does not check what you required: add
`--require tsconfig-paths/register` yourself for path aliases. If the source
then fails to load, the error says what the loader must do:

```txt [Output]
nest-graph-inspector: Loading src/app.module.ts failed: Invalid or unexpected token
src/app.module.ts is TypeScript, loaded through --require dotenv/config: the loader must register .ts files and emit the decorator metadata Nest reads (--require ts-node/register does both).
```

The export never installs or chooses a loader for you; see
[TypeScript, without building](#typescript-without-building).

## Monorepos

In a [Nest CLI monorepo](https://docs.nestjs.com/cli/monorepo), `--app`
chooses the application by its name under `projects` in `nest-cli.json`:

```bash [Terminal]
npx nest-graph-inspector export --app worker
```

Without `--app`, the export uses the default project — what `nest build`
builds given no name, from the top level of `nest-cli.json` alone; a
project's own settings apply only with `--app` — and says which one, for an
`app.module.js` found by convention too, naming the file instead when it is
not plainly that project's own:

```txt [Output]
nest-graph-inspector: nest-cli.json defines applications api, worker; using the default project api (pass --app <name> for another)
```

When the top level names no default project, pass `--app`, unless the
convention finds an `app.module.js` first. `--app` takes applications only: a
library has no `main.ts`.

Applications can share an `outDir`, and an older build can leave files in it,
so the export takes only what is plainly the application's own:

- With `--app`, only the `app.module.js` its build writes — never one found by
  searching the `outDir` — and none when its build could have written it to
  more than one place. Failing that, its `main.ts` decides.
- A compiled root module another application's build also writes — from a
  source at the same path, or at another through its own `rootDir` — is never
  loaded. A webpack or rspack application never counts: it writes one bundle.
  With a `--require`, the export loads the application's own TypeScript
  source instead; without one, it stops and names both files.
- When nothing of the application is built, the message names
  `nest build <app>`.

An application is built as the Nest CLI builds it. A monorepo `nest g app`
made has `"builder": "rspack"` — older Nest CLIs wrote `"webpack": true` — so
each application is one bundle the export will not load: export its
TypeScript source, with its own tsconfig and your libraries' path aliases:

```bash [Terminal]
TS_NODE_PROJECT=apps/api/tsconfig.app.json npx nest-graph-inspector export --app api \
  --require ts-node/register --require tsconfig-paths/register
```

A monorepo whose `nest-cli.json` names no builder is built with `tsc` and
exported from its compiled files, as is an application built with `"tsc"` or
`"swc"`. Nest CLI 12 and 11 lay out SWC's output for a source root like
`apps/api/src` differently; when both layouts are there, one is stale and the
export loads neither — pass `--entry`, build again into an emptied `outDir`,
or load the TypeScript source with `--require`.

## If `main.ts` loads your environment

The export loads your root module and never selects `main.ts` to load —
though a module file that imports `main.ts` still loads it
([Limitations](#your-module-files-still-run)). If `main.ts` loads
environment variables that a module file reads as it loads —
`import 'dotenv/config'` on its first line, say — pass them with `--env-file`:

```bash [Terminal]
npx nest-graph-inspector export --env-file .env
```

It is repeatable and needs Node.js 20.12 or later; as with `node --env-file`,
your environment beats a file, and a later file an earlier one. On older
Node.js, or to load the environment exactly as `main.ts` does, require dotenv
instead:

```bash [Terminal]
npx nest-graph-inspector export --require dotenv/config
```

Without either, the export fails as your application would, with your
configuration's error for the missing variable.

## How it works

The export boots your application in NestJS's **preview mode**, which Nest
provides for
[drawing an application's graph in CI](https://docs.nestjs.com/devtools/ci-cd-integration).

::steps
### Load your module files
The file exporting your root module, such as `dist/app.module.js` or the one
[found from `main.ts`](#how-the-root-module-is-found), is loaded with every
module file it imports. The export never selects `main.ts` as that file, and
refuses a selected file that would start the application. The files it
imports are not checked, so one that imports `main.ts`, or another file that
boots your application, still starts it
([Limitations](#your-module-files-still-run)).

### Boot in preview mode
`NestFactory.create(AppModule, { preview: true, snapshot: true })`. Nest scans
every module and resolves every dependency — a provider it cannot resolve fails
the export, as it would your application — but calls no constructor,
`useFactory`, lifecycle hook (`onModuleInit`, `onApplicationBootstrap`,
`onModuleDestroy`, …), or `configure()`. The application is never initialized
and never listens.

### Build the graph
The code behind a running application's `/output.json` builds the graph with
your `NestGraphInspectorModule.forRoot()` options, reading JSDoc and Direct Run
parameter types from your TypeScript sources as at runtime.
::

## Options

| Option | Default | What it does |
|---|---|---|
| `--entry <file>` | Detected | The file exporting your root module: compiled JavaScript, or TypeScript with a `--require` loader. If unset, it is [detected](#how-the-root-module-is-found) from `nest-cli.json`'s `sourceRoot` and `nest build`'s tsconfig `outDir` — `dist/app.module.js`, `dist/src/app.module.js`, or the only `app.module.js` under `outDir` — else from the module `main.ts` boots. If set, `main.ts` is not read. The file is refused if it would start the application; the files it imports are not checked |
| `--module <name>` | Detected | The root module's export name. If unset: the module `main.ts` boots, when the entry came from `main.ts`; otherwise `AppModule`, or — if `AppModule` is missing or not a Nest module — the file's only Nest module export |
| `--app <name>` | Default project | In a [monorepo](#monorepos), the application to export, by its name under `projects` in `nest-cli.json`. No effect with `--entry` |
| `-o, --out <file>` | `nest-graph.json` | Where to write the graph; `-` for stdout |
| `-p, --project <dir>` | Current directory | The project root. The export runs there, so `.env` files and `tsconfig.json` resolve as at startup |
| `--env-file <file>` | — | Environment variables to load first, when [`main.ts` loads them](#if-maints-loads-your-environment). Repeatable; Node.js 20.12 or later |
| `-r, --require <module>` | — | A module to load first, resolved from the project, such as `ts-node/register` or `dotenv/config`. Repeatable |
| `--compact` | Off | One-line JSON, byte for byte as `/output.json` serves it, instead of indented |
| `-h, --help` | | Show help |
| `-v, --version` | | Show the version |

`--entry`, `--out`, `--project`, and `--env-file` are relative to where you run
the command.

::callout{icon="i-lucide-triangle-alert" color="warning" title="Never point --entry at main.js"}
`main.js` calls `bootstrap()`: loading it would start your application. So
before loading the file `--entry` names, the export refuses it when it calls a
`NestFactory` method — `main.js` compiled by `tsc` or bundled by webpack, or
`main.ts` itself — or is your application's entry file, even through a
symlink. Only that file is checked, not what it imports: the modules it
imports load with it, unread, so it must not import `main.ts` or another file
that boots your application. Point `--entry` at the compiled file exporting
your root module, such as `dist/app.module.js`.
::

### TypeScript, without building

```bash [Terminal]
npx nest-graph-inspector export --require ts-node/register
```

With nothing compiled it can load — no build yet, or a webpack or rspack
bundle — the export loads the root module `main.ts` boots from its TypeScript
source, through the loader `--require` names; add
`--require tsconfig-paths/register` when your imports use `paths` aliases. Once
the project is built, its compiled files win; to load the TypeScript source
anyway, name it with `--entry src/app.module.ts`.

The loader must emit the decorator metadata Nest reads constructor dependencies
from: `ts-node` does, esbuild-based ones such as `tsx` do not, and SWC does only
with `decoratorMetadata` enabled. Without it, Nest sees only dependencies with
an explicit `@Inject()` token, and the graph silently lacks the rest.

### On standard output

```bash [Terminal]
npx nest-graph-inspector export --out - --compact > graph.json
```

Only the graph goes to stdout. The summary, warnings, Nest's errors, and
whatever your application writes through `process.stdout` — `console.log` in a
module file, Nest's logger, even a timer firing after the export — go to
stderr. A logger writing straight to file descriptor 1, such as pino's
`pino.destination(1)`, bypasses this: write the graph to a file instead.

### Exit codes

| Code | Meaning |
|---|---|
| `0` | Graph written |
| `1` | Export failed: no entry file, no root module export, a file that would start the application, or Nest could not bootstrap the application |
| `2` | Invalid command line, or an `--app` that names no application in `nest-cli.json` |

## Options from your application

Like a running inspector, the export applies the options your application gives
`NestGraphInspectorModule`:

- **`forRoot({ … })` or a plain import**: `rootModule`, `ignore`,
  `nestCoreModuleName`, and `nestCoreProviders` apply; the root is
  `rootModule`, else the module importing the inspector.
- **No `NestGraphInspectorModule`**: the defaults, with your entry module as
  the root.
- **`forRootAsync()`**: the same as with none, plus a warning, since preview
  mode never runs the factory its options come from.

`outputs` are ignored: the export serves nothing and writes only the graph.

Run from another copy — a global install, or `npx nest-graph-inspector@latest`
— the export hands over to your project's, the only copy that recognizes your
application's `NestGraphInspectorModule`. A project copy too old to include the
CLI cannot take over: the export warns you to upgrade and uses the defaults,
with your entry module as the root.

## Viewing the file

Open the [Graph Viewer](/view) and drop `nest-graph.json` anywhere on the page,
or press **Open Graph File**; when already viewing a graph — the in-browser
example or your own application's — choose **Open Graph File…** from the
header's **File** menu. The navigator, module deep dives, and Issues page work
as for a running application.

The file stays in your browser, read with the browser's file API: it is never
uploaded, nothing is fetched or started on its behalf, and neither its name nor
its contents reach the site's analytics. Files up to 20 MB open; the tab keeps
a graph across a reload if it fits the tab's storage, about 1.5 MB of JSON, and
asks for a larger one again.

Any `GraphOutput` opens: an export, the `json` output, or a saved
`/output.json`. Format 2 or earlier asks for a newer export; a format newer
than the viewer opens with a notice that something may be missing.

**AI Chat** works on the file too, with the same
[browser requirements](/getting-started/requirements#browser), but only by
looking things up in the graph: its other mode answers from an excerpt of the
Markdown summary a running inspector serves at `/output.md`, which a file
lacks, and its mode button says so.

As plain JSON, the file can also be committed and diffed when a change rewires
modules, kept as a CI artifact, or validated against the
`GRAPH_OUTPUT_JSON_SCHEMA` the package exports.

### What a graph file cannot do

With no application behind the file, the viewer turns off what needs one and
says why where you would look for it:

- **Direct Run**: there is no instance to call, though the drawer still lists
  each provider's methods.
- **Trace**: traces record Direct Run calls against a running application.
- **Saving a layout to your project**: the tab keeps your arrangement, and
  **Download layout** saves it as `nest-graph-layout.json`. To start a running
  inspector from it, rename it `.muse` and put it in your project's root, the
  one place the inspector reads a layout from.

## Limitations

### Your module files still run

Preview mode instantiates nothing, but loading your module files runs the
top-level code of every file they import:

- Decorators are evaluated, and with them every dynamic module call in an
  `imports` array: `ConfigModule.forRoot()` reads your `.env` file,
  `TypeOrmModule.forRoot({ … })` builds its options, and a `forRoot()` that
  throws fails the export.
- `forwardRef()` callbacks run, and promises in an `imports` array are awaited.
- A module file that imports `main.ts`, or another file that boots the
  application, starts it: the export checks the file it loads, not the files
  that one imports.
- Environment variables read at import time must be set, as for `nest start`:
  in your environment, or with `--env-file` or `--require dotenv/config`.
- Nest initializes the modules on its preview allowlist: in NestJS itself only
  `InternalCoreModule`, but a library can add its own, whose providers are then
  constructed and whose hooks run.

### Options Nest serializes

Under the export's `snapshot: true`, Nest builds each dynamic module's key with
`JSON.stringify` of its metadata, so a `forRoot()` or `register()` whose
options hold a circular object or a `BigInt` fails the export —
`Converting circular structure to JSON`, or
`Do not know how to serialize a BigInt` — though your application, started
without `snapshot`, does not.

### What a running application would add

- **Direct Run methods of `useFactory` and `useExisting` providers**, which a
  running inspector reads off the instance: the value a factory returned, or
  the provider an alias points at. Preview mode calls no factory and resolves
  no alias, so an export has no `directRun` for them.
- **Anything added at runtime**: modules loaded with `LazyModuleLoader`, or
  providers registered from a factory or a hook, exist only once the
  application runs.

Everything else — modules, imports, exports, providers, controllers, their
dependencies, JSDoc, routes, and cycles — matches the graph a running inspector
serves.
